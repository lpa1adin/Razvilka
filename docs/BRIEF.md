# ТЗ: «Развилка» — платформа практического обучения разработке

> Рабочее название. Версия ТЗ 1.0 · 2026-10-30 · составлено по шаблону `web-base/brief/brief-template.md`.
> Архитектурные решения с вариантами и обоснованием — в [`DECISIONS.md`](DECISIONS.md),
> правила независимого ревьюера — в [`REVIEWER.md`](REVIEWER.md).

---

## 1. Суть

- **Проект:** локальная веб-платформа, где владелец учится разработке на практике. Платформа даёт проверенную
  теорию, тесты и задания с автопроверкой, учит читать и проектировать архитектуру, а встроенный Claude
  собирает курсы по реальным проектам владельца и оценивает его решения.
- **Задача:** каждый день открыть платформу, продолжить с места остановки, выполнить урок
  (теория → тест → практика → развилка) и получить оценку.
- **Тип:** веб-приложение, персональное, работает локально (v1).
- **Мера успеха:**
  1. Владелец сам, без подсказок, называет тип архитектуры чужого проекта (монолит / модульный монолит /
     микросервисы), его окружение (БД, кэш, очередь, мониторинг, контейнеры, прокси) и устройство кода
     (классы и их поля, функции, слои).
  2. Владелец заново пишет свой проект (например, `fisht-trails`) по пути, который собрала платформа, и проходит
     все проверки.
  3. По каждой развилке владелец может назвать варианты, выбранный и причину выбора. Оценка Claude растёт.

## 2. Аудитория и роли

- **Пользователь v1 — один, владелец.** Работает за компьютером. Знает основы вёрстки, делал сайты
  (`fisht-trails`, `kalon`, `autocheck`).
- **Что его волнует:** понять, *почему* код написан именно так, а не просто прочитать его. Учиться на своих
  проектах. Доверять теории, поэтому в ней только проверенные источники.
- **Роли — две, с входом по логину и паролю:**

  | Действие | Пользователь | Админ |
  | --- | :---: | :---: |
  | Читать теорию, проходить уроки и тесты, решать задания в песочнице | ✓ | ✓ |
  | Отправлять свой проект (или этап проекта) на проверку и видеть оценку | ✓ | ✓ |
  | Задавать наставнику вопросы по текущему уроку (без создания контента) | ✓ | ✓ |
  | Видеть свой журнал развилок, прогресс и отчёты | ✓ | ✓ |
  | Выбрать проект и сгенерировать на его основе новый курс или задание | — | ✓ |
  | Редактировать, снимать с публикации и публиковать курсы, задания, вопросы, привязку теории | — | ✓ |
  | Управлять источниками, сборщиком, рубриками и правилами ревьюера | — | ✓ |
  | Видеть прогресс и сданные работы пользователей | — | ✓ |

  Пользователь видит **только опубликованное**. Всё, что сгенерировано, сначала становится черновиком у
  админа и попадает к пользователю только после его проверки. Владелец может работать под двумя
  учётками: как админ готовит курс, как пользователь его проходит.
- **Агенты (не люди, но со своими правами):**
  | Агент | Что делает | Что может |
  | --- | --- | --- |
  | **Наставник** (чат) | Пользователю — отвечает на вопросы по уроку. Админу — ещё и собирает курсы, задания и тесты | Читать библиотеку. В режиме админа — читать проекты и создавать **черновики** (публикует только админ) |
  | **Оценщик** | Оценивает сданную работу целиком: ответы на развилки **вместе с кодом**, который их реализует, по рубрике и с эталонами | Только чтение. Видит ответы, код, рубрику и эталоны, но не переписку с наставником |
  | **Ревьюер** | Проверяет код по правилам [`REVIEWER.md`](REVIEWER.md) | Только чтение. Новая сессия на каждую проверку, без контекста автора |
  | **Сборщик** | По расписанию забирает теорию из белого списка открытых источников | Сеть только к доменам из белого списка, запись в библиотеку |

## 3. Контент

### 3.1 Теория: только из проверенных источников
Claude **не пишет** теорию сам: он подбирает, связывает и объясняет, *зачем* это читать.
У каждого фрагмента теории есть карточка источника: автор, название, издание или версия, глава/раздел,
URL, лицензия и дата импорта.

Как фрагмент попадает на платформу, решает лицензия источника. Это обязательное правило, его проверяет код:

| Лицензия источника | Что показываем на платформе |
| --- | --- |
| Открытая, разрешает переиспользование (CC BY, CC BY-SA, CC BY-NC-SA, PSF, PostgreSQL License, MIT) | Полный текст фрагмента с атрибуцией и ссылкой; изменения помечаются |
| Бесплатна для чтения, но без права копирования (CC BY-NC-ND, «все права защищены» на сайте) | Ссылка на конкретный раздел, короткая цитата до 15 слов, вопросы «на что обратить внимание» |
| Книги | Библиографическая ссылка (глава, страницы), что в ней искать, связь с уроком. Текст книги не копируется |

**Стартовый белый список** (лицензии сборщик перепроверяет при импорте):

- **Веб (HTML/CSS/JS):** MDN Web Docs (CC BY-SA), learn.javascript.ru (*уточнено на этапе 1:* по сути CC BY-NC, но автор просит согласовывать любое использование, кроме чтения, — поэтому режим «ссылка + оглавление», ADR-014), web.dev Learn (CC BY),
  The Odin Project (CC BY-NC-SA).
- **Python:** документация python.org (PSF), «Think Python» Аллена Дауни (открытая лицензия),
  «Automate the Boring Stuff» Эла Свейгарта (CC BY-NC-SA).
- **SQL и данные:** документация PostgreSQL, «Use The Index, Luke» Маркуса Винанда (ссылки);
  «Designing Data-Intensive Applications» Мартина Клеппмана (книга, только ссылки).
- **Архитектура:** The Twelve-Factor App, C4 model (CC BY), microservices.io (Крис Ричардсон, ссылки),
  статьи Мартина Фаулера (ссылки), Google SRE Book (CC BY-NC-ND, только ссылки и цитаты),
  Azure Architecture Center, ADR (adr.github.io); книги «Clean Architecture» (Роберт Мартин),
  «Building Microservices» (Сэм Ньюмен), «Design Patterns» (GoF) — только ссылки.
- **Контейнеры и мониторинг:** документация Docker, Prometheus, Grafana.
- **Курсы:** CS50 (Harvard, CC BY-NC-SA), MIT OCW 6.031 Software Construction (CC BY-NC-SA), freeCodeCamp.

### 3.2 Эталонные проекты для оценки
Оценщик сравнивает работы владельца с открытыми проектами, архитектура которых известна и описана авторами:

- `gothinkster/realworld` — одно приложение во множестве реализаций (монолиты на разных стеках).
- `fastapi/full-stack-fastapi-template` — full-stack монолит: Docker, Postgres, тесты, CI.
- `GoogleCloudPlatform/microservices-demo` (Online Boutique) — микросервисы, gRPC, k8s, наблюдаемость.
- `microservices-demo/microservices-demo` (Sock Shop) и `dotnet/eShop` — микросервисы с очередями.
- `donnemartin/system-design-primer` — разборы системного дизайна.
- **Сама «Развилка»** — модуль 0: владелец разбирает архитектуру платформы, на которой учится
  (ответ есть в `DECISIONS.md`).

### 3.3 Вопросы, задания, курсы
- **Банк вопросов:** не меньше 50 вопросов на тему. У каждого есть подтема, сложность, ссылка на источник
  и объяснение правильного ответа.
- **Задания песочницы:** условие, стартовый код, эталонное решение и автотесты. Задание публикуется, только
  если эталонное решение проходит свои тесты: это проверяется автоматически.
- **Тексты интерфейса** пишу я, по-русски. Язык интерфейса один, русский.


## 5. Функциональность

### 5.1 Курсы и уроки
- Курс → модули → уроки. Урок состоит из блоков: теория (фрагменты из библиотеки), тест, практика, развилка.
- Прогресс сохраняется по каждому блоку. «Продолжить» открывает первый незавершённый.
- **Крайние случаи:** источник пропал или сменил лицензию → фрагмент помечается «нужно обновить», урок
  остаётся доступным со ссылкой на архив (web.archive.org).

### 5.2 Тесты без повторов
- **Кто → что → результат:** владелец запускает тест по теме и получает 10 вопросов из банка темы.
- **Алгоритм подбора:**
  1. Сначала вопросы, которые владелец ещё не видел.
  2. Если невиданных меньше 10 — добираем те, что были давно, и в первую очередь те, где он ошибся.
  3. Внутри выборки — равномерно по подтемам и сложностям.
  4. Когда виден весь банк, начинается новый цикл, а порядок и варианты ответов перемешиваются.
- **Типы вопросов:** один ответ, несколько ответов, порядок шагов, сопоставление, «найди ошибку в коде»,
  «определи архитектуру по схеме / docker-compose / дереву файлов».
- **После теста:** балл, разбор каждой ошибки со ссылкой на источник, кнопка «Повторить ошибки».
- **Крайние случаи:** в банке меньше 10 вопросов → тест короче, с предупреждением. Тест прерван → можно
  продолжить, попытка не засчитывается до завершения.

### 5.3 Песочница с проверкой
- **HTML/CSS/JS:** код выполняется в изолированном iframe, превью обновляется на лету. Проверка запускает
  тесты задания внутри iframe: структура DOM, вычисленные стили, поведение по клику, адаптив на заданной
  ширине.
- **Python:** выполняется в браузере (Pyodide, отдельный поток с лимитом времени). Тесты — вызовы функций и
  классов владельца с ожидаемыми результатами.
- **SQL:** SQLite в браузере (*уточнено на этапе 2:* через `sqlite3` в Pyodide, ADR-006) с подготовленной схемой. Проверка сравнивает результат запроса с
  эталоном и, если задано, структуру созданных таблиц.
- Проверяется **поведение, а не совпадение текста**. Решение, написанное иначе, чем эталон, засчитывается.
- **Крайние случаи:** бесконечный цикл → остановка по таймауту и понятное сообщение. Синтаксическая
  ошибка → строка и пояснение. Код сохраняется автоматически.

### 5.4 Тренажёр архитектуры
Учит определять архитектуру на двух уровнях.

| Уровень | Что дают | Что нужно определить |
| --- | --- | --- |
| **Верхний** | `docker-compose.yml`, k8s-манифесты, дерево репозитория, схема развёртывания реального открытого проекта | Монолит / модульный монолит / микросервисы / serverless; какие смежные сервисы есть (БД, кэш, брокер, мониторинг, логи, CI/CD, прокси) и как они связаны; где выполняется каждая часть |
| **Нижний** | Фрагмент кода реального проекта | Парадигму (ООП / функциональная / процедурная); классы, их поля и методы, связи (наследование, композиция); структуру функций и граф вызовов; слои и паттерны |

- Задания идут по нарастающей: «выбери из вариантов» → «собери схему из блоков» (drag-and-drop) →
  «опиши своими словами». Последнее оценивает Оценщик.
- По коду платформа строит диаграммы автоматически (дерево файлов, классы, вызовы). Сначала владелец
  рисует сам, потом сравнивает со сгенерированной схемой.

### 5.5 Разбор проектов («напиши заново сам»)
Владелец не просто читает чужой код, а пишет проект сам с нуля, по шагам.

1. **Выбор проекта (админ):** любая папка из `ProjectsWithClaude/` (подключена только на чтение) или
   открытый репозиторий из списка эталонов.
2. **Карта проекта:** статический анализ без Claude: дерево файлов, языки, зависимости, точки входа,
   классы с полями, функции и вызовы. Claude добавляет пояснения: какую роль играет каждая часть.
3. **Путь сборки:** Claude разбивает проект на этапы, от пустой папки до готового сайта. В каждом этапе:
   цель, какие файлы создать, теория из библиотеки, **развилки** (какие варианты были, ответ автора
   скрыт до ответа владельца) и проверка.
4. **Рабочая папка:** для владельца создаётся отдельная папка `workspace/<проект>/` (оригинал не
   трогается). Писать можно в своём редакторе (VS Code) или во встроенном. Платформа запускает этапный
   локальный сайт-превью этой папки.
5. **Проверка этапа:** «Сдать на проверку» (§5.11). Автотесты, Ревьюер и Оценщик проверяют код вместе с
   ответами на развилки этапа. Этап засчитывается, когда тесты проходят и оценка не ниже порога (по
   умолчанию 3 из 5).
- Пути «напиши заново сам» создаёт админ в Мастерской (§5.10). Пользователь видит только опубликованные
  пути, в разделе «Мои проекты».
- **Крайние случаи:** проект слишком большой → разбор только выбранной части (папки/модуля). Язык не
  поддерживается анализатором → карта только по файлам, без классов.

### 5.6 Развилки и оценка решений
Главная механика: Claude не говорит «сделай», а выносит решение на обсуждение.

- Развилка — вопрос с контекстом: «Для хранения прогресса нужна БД. Какую выбрать и почему?»
- **Ответ владельца:** выбранный вариант, рассмотренные альтернативы, причины, риски, когда решение
  пересмотреть. Форма повторяет формат ADR, по которому записаны решения самой платформы.
- **Оценщик проверяет ответы вместе с практической реализацией.** Отдельно ответ на развилку
  оценивается только в теоретических уроках. Если к развилке есть код, Оценщик получает:
  ответы пользователя, его код (папку или сдачу), результаты автотестов, отчёт Ревьюера, рубрику и эталоны.
- **Рубрика (0–5 по каждому критерию):**

  | Блок | Критерий |
  | --- | --- |
  | Обоснование | 1. Названы реальные альтернативы |
  | | 2. Компромиссы описаны верно |
  | | 3. Выбор подходит к контексту проекта (масштаб, нагрузка, команда) |
  | | 4. Есть опора на источники или эталоны; указано, когда пересмотреть |
  | **Реализация** | 5. **Код соответствует заявленному решению.** Сказал «PostgreSQL + миграции» — в коде Postgres и Alembic, а не SQLite и ручной SQL |
  | | 6. Решение реализовано правильно: тесты проходят, у Ревьюера нет `blocker` по этому месту |
  | | 7. Заявленные свойства видны в коде. Сказал «модули разделены» — нет импортов через слои; сказал «микросервисы» — у сервисов свои данные и явные контракты |
  
- **Расхождение «сказал ≠ сделал»** — отдельный, самый заметный пункт отчёта: цитата ответа рядом со
  ссылкой `файл:строка`, где реализация говорит другое. Такое расхождение снижает итог сильнее, чем
  просто слабое обоснование.
- К каждому баллу — пояснение со ссылками на код пользователя, эталонные проекты и источники, плюс
  «что сделали бы в эталоне и почему».
- Оценка учитывает **общую картину проекта**: предыдущие развилки и сдачи пользователя в этом же проекте.
  Противоречие с ранее выбранным — отдельное замечание.
- **Независимость:** у Оценщика, как и у Ревьюера, новая сессия на каждую оценку, доступ только на
  чтение и нет доступа к чату-помощнику. Рубрику меняет только админ.
- **Оценщик и Ревьюер не дублируют друг друга.** Ревьюер ищет дефекты кода по правилам. Оценщик судит,
  насколько решение продумано и совпадает с реализацией, и использует отчёт Ревьюера как вход.
- Все развилки собираются в журнал. Его можно выгрузить в `docs/DECISIONS.md` своего проекта.

### 5.7 Чат-помощник (пользователь)
- Открывается панелью на любом экране и знает контекст: текущий урок, задание и код пользователя.
- Объясняет и наводит на решение, отвечая ссылками на теорию урока. **Готовое решение задания не выдаёт:**
  подсказки идут по нарастающей, и каждая использованная подсказка отмечается в попытке.
- Не создаёт и не меняет контент. На просьбу «сделай курс» отвечает, что курсы создаёт админ, и
  предлагает отправить админу заявку на тему (она появляется в Мастерской → Генерация).
- Ответы идут потоком, по мере генерации.
- **Крайние случаи:** Claude недоступен (нет сети, исчерпан лимит) → понятное сообщение, а уроки, тесты и
  песочница работают без него.

### 5.8 Сборщик открытых источников
- Работает по расписанию (раз в неделю) и по запросу наставника.
- Забирает материалы только с доменов из белого списка, а MDN и learn.javascript.ru — из их открытых
  репозиториев на GitHub. Режет текст на фрагменты, индексирует для поиска, сохраняет лицензию и версию.
- Повторный импорт показывает, что изменилось в источнике. Уроки с изменёнными фрагментами помечаются.
- **Практикум «Построй свой агрегатор»:** финальный проект курса по архитектуре. Владелец проектирует
  похожий сборщик (концепция, схема C4, развилки, хранение, связи между сервисами), затем пишет его.
  Оценщик сравнивает работу с устройством сборщика платформы и с эталонами.

### 5.9 Независимый ревьюер кода
Правила — в [`REVIEWER.md`](REVIEWER.md). Независимость обеспечивается технически, а не обещанием:

- Каждая проверка — новая сессия без истории чата и без знания, кто и зачем писал код.
- На входе только условие задачи, код или изменения и правила. Инструменты только на чтение.
- Ответ — строгий JSON: замечания с id правила, серьёзностью, файлом:строкой, объяснением и ссылкой на
  источник.
- Ревьюер не исправляет код, он только находит проблемы.
- Тот же набор правил выгружается как агент Claude Code (`.claude/agents/reviewer.md`), чтобы проверять
  проекты вне платформы.

### 5.10 Мастерская: как создаются задания (только админ)
Генерация идёт по шагам. На каждом шаге есть статус, и к пользователю ничего не попадает без решения
админа.

```
Заявка ─► План ─► Черновик ─► Автопроверки ─► Проверка админом ─► Опубликовано ─► (новая версия)
 админ    Claude    Claude       код              админ                  виден юзеру
 или юзер  + правки
           админа
```

1. **Заявка.** Админ выбирает **источник задания**: папку проекта из `ProjectsWithClaude/`, открытый
   эталонный репозиторий или тему без проекта. Затем выбирает, **что создать**: курс целиком / модуль /
   одно практическое задание / набор вопросов / развилку / путь «напиши заново сам». Указывает уровень
   сложности и, если нужно, конкретную часть проекта (папку, файл, функцию). Заявки пользователей на тему
   попадают сюда же, их админ принимает или отклоняет.
2. **План.** Наставник строит карту проекта (§5.5) и предлагает план: что будет в каждом уроке, какие
   развилки, какая теория из библиотеки, какие проверки. Админ правит план: удаляет, переставляет, меняет
   формулировки, просит переделать часть. Без утверждённого плана черновик не создаётся.
3. **Черновик.** Наставник создаёт содержимое по плану: условие, стартовый код, эталонное решение,
   автотесты, подсказки, вопросы со ссылками на источники, развилки с ответом автора проекта и рубрикой.
   Задача выполняется в фоне, прогресс виден по шагам.
4. **Автопроверки — код, без Claude.** Черновик не идёт дальше, пока:
   - эталонное решение проходит все свои тесты, а стартовый код — **не** проходит (иначе задание пустое);
   - у каждого фрагмента теории и каждого вопроса есть источник с допустимой лицензией;
   - у вопроса ровно один правильный ответ (или явно отмечен множественный выбор);
   - вопрос не дублирует уже существующие в банке темы (проверка похожести формулировок);
   - независимый Ревьюер проверил эталонное решение по `REVIEWER.md`: эталон не должен учить плохому.
5. **Проверка админом.** Экран «черновик ↔ превью глазами пользователя». Админ редактирует любое поле
   вручную в том же редакторе, что и в песочнице, и может перезапустить автопроверки. Ещё можно
   попросить наставника переделать только выбранный блок («усложни тесты», «замени теорию»).
6. **Публикация.** Админ нажимает «Опубликовать», и задание появляется у пользователя.
7. **Версии.** Правка опубликованного создаёт новую версию. Начатые попытки пользователей остаются на
   своей версии, новые идут на последнюю. Задание можно снять с публикации — тогда прогресс сохраняется,
   но задание скрывается. Есть история изменений: кто, когда, что поменял.

**Ручное создание.** Всё то же самое админ может создать без Claude, через форму. Автопроверки обязательны
и в этом случае.

### 5.11 Сдача проекта на проверку (пользователь)
- **Что можно сдать:** этап пути «напиши заново сам», задание-практикум (например, «свой агрегатор») или
  свой проект целиком. Способы: рабочая папка `workspace/<проект>/`, zip-архив или ссылка на публичный
  git-репозиторий.
- **При сдаче пользователь заполняет:** ответы на развилки этапа (если есть) и короткое описание
  «что сделал и почему».
- **Что происходит после «Сдать»:**
  1. Автотесты этапа в сервисе `runner` (код, без Claude): сайт открывается в Chromium на 375 / 768 / 1280,
     Python-код проверяется через pytest.
  2. Ревьюер — замечания по коду (`REVIEWER.md`).
  3. Оценщик — **итоговая оценка ответов вместе с реализацией** (§5.6).
- **Пользователь видит** статус по шагам, а затем общий отчёт: тесты ✓/✗, замечания ревьюера, оценку по
  критериям. Можно исправить и сдать повторно. Все сдачи хранятся, видна динамика.
- **Крайние случаи:** архив слишком большой или битый → понятная ошибка до отправки. В архиве есть
  `node_modules`, `.env`, секреты → они отбрасываются, а пользователь получает предупреждение.

- **Палитра (черновик токенов):** фон `#0B0D10` → градиент к `#1A1D22`; поверхности `#12151A`;

  со свечением; Claude и ИИ — янтарный `#F5A524`; ошибка `#F87171`. Контраст текста — не ниже AA.
- **Шрифты:** интерфейс — Manrope (геометрический, с кириллицей; ближе всего к Cera CY из референса);
  крупные заголовки — капслок с разрядкой; код — JetBrains Mono.
- **Анимации — умеренные, только там, где не мешают работе:**
  - Главная: частицы, плавающие фрагменты кода с параллаксом, строка терминала, которая печатает
    приветствие.

  - Экраны урока, редактор и тесты — **без фоновой анимации**. Только состояния: проверка, ✓/✗.
  - Всё выключается при `prefers-reduced-motion`.
- **Запреты:** кислотные неоновые градиенты на всё, «матрица» из падающих символов, анимация под
  редактором.

## 7. Нефункциональные требования
- **Устройства:** в первую очередь ноутбук и монитор (1280 / 1440). Планшет и телефон (768 / 375) —
  чтение теории, тесты, журнал, чат. На телефоне песочница доступна, но работает упрощённо, вкладками.
- **Браузеры:** последние 2 версии Chrome, Safari, Firefox, Edge.
- **Доступность:** контраст AA, полная работа с клавиатуры (в том числе тесты), `prefers-reduced-motion`.
- **Скорость:** интерфейс открывается меньше чем за 2 с локально; Pyodide и Monaco загружаются только на
  экранах практики.
- **Доступ:** вход по логину и паролю (хэш Argon2), сессия в httpOnly-cookie. Права проверяет **сервер** на
  каждом запросе, а не только интерфейс: пользователь не получит черновики и экраны Мастерской даже по
  прямой ссылке или запросу к API. Первый админ создаётся командой при установке. Публичной регистрации
  нет — учётки создаёт админ.
- **Безопасность:** код из песочницы выполняется только в изолированном iframe / Web Worker без доступа к
  API платформы. Сданные проекты выполняются в `runner`: отдельный пользователь, таймаут, временная папка,
  нет интернета, `docker.sock` не монтируется. Проекты владельца подключены только на чтение. Секреты лежат в `.env`, не в git. Сборщик
  ходит в сеть только по белому списку.
- **Наблюдаемость:** метрики API и агентов (запросы, ошибки, длительность, расход лимита Claude) видны
  в Grafana. Это и рабочий инструмент, и учебный пример мониторинга.

## 8. Техническая реализация
Подробно, с рассмотренными вариантами, — в [`DECISIONS.md`](DECISIONS.md). Кратко:

| Слой | Решение |
| --- | --- |
| Архитектура | **Модульный монолит + фоновые воркеры**: одна кодовая база бэкенда, процессы `api`, `agent-worker`, `collector`, `runner`. Не микросервисы (ADR-001) |
| Фронтенд | React + Vite + TypeScript + Tailwind + react-router; редактор Monaco; диаграммы React Flow (ADR-005) |
| Бэкенд | Python 3.12 + **FastAPI**, SQLAlchemy 2 + Alembic (ADR-002) |
| Данные | **Только PostgreSQL 16**: реляционное ядро + JSONB + полнотекстовый поиск по-русски + очередь + сессии. Без Redis и MongoDB — они изучаются в отдельных уроках (ADR-003, ADR-004) |
| Очередь задач | Таблица в Postgres (`SELECT … FOR UPDATE SKIP LOCKED`), без Redis в v1 (ADR-004) |
| Выполнение кода | Песочница — в браузере: iframe (HTML/CSS/JS), Pyodide (Python), sql.js (SQL). Сдачи и эталоны — сервис `runner`: Playwright + pytest, без интернета, с лимитами (ADR-006) |
| Claude | **Claude Agent SDK (Python)** на подписке владельца, в отдельном контейнере `agent-worker` (ADR-007) |
| Анализ кода | tree-sitter: дерево, классы, функции, вызовы для Python / JS / TS / HTML / CSS (ADR-008) |
| Запуск | **Docker Compose**: `web`, `api`, `agent-worker`, `collector`, `runner`, `postgres`, `prometheus`, `grafana`. Одна команда: `docker compose up` (ADR-009) |
| Хранение | Данные — том Postgres; рабочие папки — `./workspace`; проекты владельца — том только для чтения |

## 10. Открытые вопросы и допущения

**Решено с владельцем (2026-10-30):** чат через Agent SDK на подписке; песочница HTML/CSS/JS + Python + SQL;
сборщик нужен и как функция платформы, и как практикум; запуск сразу в Docker Compose.
**Решено (2026-10-30, стек):** FastAPI; модульный монолит; только PostgreSQL; песочница в браузере +
`runner` для сдач. По умолчанию: Monaco, очередь в Postgres, tree-sitter.
**Решено (2026-10-30, обсуждение):** две роли — пользователь и админ; задания генерируются только в
Мастерской админа по шагам с публикацией вручную; Оценщик проверяет ответы вместе с реализацией.

**Допущения (по умолчанию, можно поправить):**
- Название «Развилка» — рабочее.
- Тёмная тема основная, светлая — в настройках.
- Интерфейс только на русском. Источники бывают и на английском; русская версия берётся, где она есть
  (MDN ru, learn.javascript.ru).
- Иконки — Lucide.
- Первый курс для проверки — по `fisht-trails`.

**Риски:**
- Использование подписки через Agent SDK допустимо для личного локального использования. Если условия
  изменятся, тот же код работает с ключом API: меняется одна переменная в `.env`.
- Лимиты подписки: сборка курса — тяжёлая задача. На дашборде виден расход; задачи ставятся в очередь.
- Лицензии источников могут меняться — сборщик перепроверяет при каждом импорте.
