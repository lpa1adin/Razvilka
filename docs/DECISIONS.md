# Журнал развилок (ADR) платформы «Развилка»

Каждое решение записано в одном формате: **контекст → варианты → решение → почему → когда пересмотреть**.
Этот файл — учебный материал модуля 0 («разбери архитектуру платформы, на которой учишься»). Отвечая на
развилки своих проектов, владелец пишет решения в том же формате.

Статусы: `принято` · `предложено` (обсуждаем) · `заменено ADR-xxx`.

---

## ADR-001. Тип архитектуры: модульный монолит + воркеры — `принято` (владелец, 2026-10-30)
**Контекст.** Один пользователь, локальный запуск, один разработчик. Есть долгие задачи: генерация
курса, оценка, импорт источников.
**Варианты.**
1. *Классический монолит* — один процесс. Проще всего, но долгая задача Claude блокирует или раздувает API.
2. *Модульный монолит + фоновые воркеры* — одна кодовая база с модулями (`courses`, `quiz`, `sandbox`,
   `library`, `agents`, `projects`, `workshop`, `submissions`, `auth`), несколько процессов: `api`,
   `agent-worker`, `collector`, `runner`.
3. *Микросервисы* — отдельный сервис и отдельная БД на каждый домен. Нужны при нескольких командах и
   независимом масштабировании. Здесь нет ни того, ни другого, а сложность (сеть, согласованность,
   развёртывание) вырастает в разы.
**Решение.** Вариант 2.
**Почему.** Долгие задачи вынесены из API, при этом нет распределённых транзакций и межсервисных
контрактов. Границы модулей проводятся сразу, чтобы модуль при необходимости можно было выделить в сервис.
**Пересмотреть, когда** появятся независимые команды или модулю понадобится своё масштабирование.
**Источники.** M. Fowler «MonolithFirst»; S. Newman «Building Microservices», гл. 1; microservices.io —
«Pattern: Monolithic Architecture».

## ADR-002. Бэкенд-фреймворк: FastAPI — `принято` (владелец, 2026-10-30)
**Варианты.**
| | FastAPI (Python) | Django + DRF (Python) | NestJS (Node/TS) | Express (Node) |
| --- | --- | --- | --- | --- |
| Agent SDK | Python SDK — нативно | нативно | TS SDK — нативно | нативно |
| Стриминг (SSE) и async | из коробки | частично (ASGI) | да | вручную |
| Схемы и валидация | Pydantic, автодокументация `/docs` | сериализаторы DRF | DTO + декораторы | вручную |
| Порог входа для чтения кода | низкий | средний (много «магии») | высокий (DI, декораторы) | низкий, но без структуры |
| Админка | нет | есть | нет | нет |
**Решение.** FastAPI.
**Почему.** Python нужен и так: Pyodide-задания, анализ кода, сборщик. Pydantic-схемы и автоматическая
OpenAPI-документация сами по себе учат проектировать API. Нативный async подходит для потокового чата.
Код легко читать при разборе.
**Цена.** Нет готовой админки. Структуру проекта задаём сами (см. ADR-001).
**Пересмотреть, когда** понадобится большая админка для контента — тогда Django.

## ADR-003. Хранилище: PostgreSQL, без NoSQL — `принято` (владелец, 2026-10-30)
**Контекст.** Данные: пользователь → курсы → модули → уроки → блоки; вопросы ↔ темы ↔ попытки ↔ ответы;
развилки ↔ оценки; источники ↔ фрагменты ↔ лицензии. Нужно полнотекстовое по-русски по теории.
**Варианты.**
1. *PostgreSQL* — связи, транзакции, JOIN для статистики («вопросы, где я ошибался»). JSONB для гибких
   структур (содержимое блока урока, тесты задания). Встроенный FTS с русской морфологией. pgvector —
   на будущее для семантического поиска.
2. *MongoDB* — гибкие документы, но почти все данные связанные. Статистика и «без повторов» требуют
   соединений и транзакций, их пришлось бы делать в коде.
3. *SQLite* — идеален для локального однопользовательского режима, но задача — практика Docker и «настоящей»
   инфраструктуры, а конкурентная запись из нескольких воркеров ограничена.
4. *Postgres + MongoDB* — две БД ради гибкости, которую уже даёт JSONB. Лишняя сложность.
**Решение.** PostgreSQL 16.
**Почему.** Данные реляционные. Гибкая часть покрывается JSONB. Поиск, очередь (ADR-004) и векторы
(в будущем) — в одной БД, меньше сервисов.
**Пересмотреть, когда** появится поток событий или логов, для которого нужна отдельная БД
(ClickHouse или Loki), или кэш с высокой нагрузкой (Redis).
**Источники.** M. Kleppmann «Designing Data-Intensive Applications», гл. 2 (модели данных);
документация PostgreSQL — JSON Types, Full Text Search.

## ADR-004. Очередь фоновых задач: таблица в Postgres — `принято` (владелец, 2026-10-30)
**Варианты.** Redis + RQ/Celery · RabbitMQ · таблица `jobs` с `FOR UPDATE SKIP LOCKED`.
**Решение.** Таблица в Postgres.
**Почему.** Задач мало (единицы в час), нужна надёжность и видимость статуса в UI. Отдельный брокер — это
ещё один сервис без выгоды.
**Пересмотреть, когда** станет нужно больше сотни задач в минуту или понадобится pub/sub. Тогда — Redis
Streams или RabbitMQ (хорошая тема для практикума).

## ADR-005. Фронтенд: React + Vite + TypeScript, редактор Monaco — `принято` (по умолчанию, 2026-10-30)
**Варианты редактора.** Monaco (движок VS Code: подсказки для JS/TS, привычные горячие клавиши; тяжёлый,
слаб на телефоне) · CodeMirror 6 (лёгкий, хорош на телефоне, подсказок меньше).
**Решение.** Monaco, загружается только на экранах практики.
**Почему.** Владелец работает за компьютером, а редактор, похожий на VS Code, переносит навыки в настоящую
работу.
**Пересмотреть, когда** практика на телефоне станет важной.

## ADR-006. Выполнение кода ученика: браузер + сервис `runner` — `принято` (владелец, 2026-10-30; уточнено на этапе 2, 2026-10-31)
**Контекст.** Сданный проект и эталон задания нужно проверять вне браузера ученика; песочница должна
отвечать мгновенно.
**Решение.**
- **Песочница (браузер).**
  - HTML/CSS/JS: страница `/sandbox.html` в iframe с `sandbox="allow-scripts"` (без `allow-same-origin`):
    у кода ученика пустое происхождение, нет доступа к cookie и API; своя CSP запрещает любые сетевые
    запросы. Проверки — в трёх скрытых iframe на ширинах 1280 / 768 / 375 параллельно.
  - Python **и SQL**: Pyodide в Web Worker; SQL — через `sqlite3` из стандартной библиотеки Pyodide.
    *Изменено против первой версии:* вместо sql.js — тот же Pyodide, чтобы логика SQL-проверок была
    одна. Зависание → поток пересоздаётся через 15 с.
- **`runner` (сервер).** Отдельный образ с Chromium (Playwright). Веб-задания — в Chromium, любые
  сетевые запросы обрываются, новая страница на каждую ширину. Python/SQL — отдельный процесс
  `python -I` без переменных окружения приложения, с лимитами CPU 10 с, памяти 1 ГБ, файлов 10 МБ,
  таймаут 15 с; контейнер без интернета.
- **Проверки пишутся один раз.** `harness/web_harness.js` и `harness/py_harness.py` — одни и те же файлы
  в браузере и в runner (интерфейс получает их через `/api/practice/harness/*`). Сборка страницы
  веб-задания есть в двух копиях (`webpage.py` и `webPage.ts`), покрыта тестом.
- *Изменено:* вместо pytest — собственный маленький харнесс: он же работает в Pyodide.
**Отвергнуто.** `docker.sock` в `runner` — фактически root-доступ к машине из сервиса, выполняющего
чужой код.
**Цена.** Образ runner ~1,5 ГБ. Проверки и ожидаемые результаты SQL видны в DevTools песочницы — для
самообучения это приемлемо: итоговую оценку при сдаче (этап 6) делает runner.
**Пересмотреть, когда** появятся чужие пользователи — одноразовые контейнеры с gVisor на проверку.

## ADR-007. Claude: Agent SDK на подписке, отдельный воркер — `принято` (владелец, 2026-10-30)
**Варианты.** Agent SDK на подписке · ключ Anthropic API · без чата в v1.
**Решение.** Claude Agent SDK (Python) в контейнере `agent-worker`. Авторизация — токен подписки в `.env`.
Проекты владельца смонтированы только для чтения.
**Почему.** Без отдельной оплаты. Агент умеет читать файлы проектов. Если сменить переменную окружения,
тот же код будет работать на ключе API.
**Три агента — три изолированные конфигурации:** Наставник, Оценщик, Ревьюер. У них разные системные
инструкции и инструменты. Оценщик и Ревьюер каждый раз начинают новую сессию.

## ADR-008. Анализ кода: tree-sitter — `принято` (по умолчанию, 2026-10-30)
**Варианты.** Свой парсер на каждый язык (`ast` для Python, TypeScript Compiler API для JS/TS) ·
tree-sitter (одна библиотека, много языков) · только Claude.
**Решение.** tree-sitter для структуры, Claude — для смысла.
**Почему.** Карта проекта детерминирована и бесплатна. Claude не «придумывает» классы, которых нет, а
объясняет найденное.

## ADR-009. Запуск: Docker Compose сразу — `принято` (владелец, 2026-10-30)
**Сервисы.** `web` (nginx + собранный фронтенд; в разработке — Vite), `api`, `agent-worker`, `collector`,
`runner` (ADR-006), `postgres`, `prometheus`, `grafana`. Сети: `public` (web ↔ api) и `internal`
(всё остальное); у `runner` нет выхода в интернет.
**Почему.** Платформа сама служит живым примером высокоуровневой архитектуры: контейнеры, сеть, тома,
мониторинг.
**Цена.** Нужен Docker Desktop, первый запуск дольше.
**Пересмотреть, когда** понадобится публикация в интернет: тогда обратный прокси с TLS и, возможно,
управляемая БД.

## ADR-010. Теория: только из источников, с учётом лицензии — `принято` (требование владельца)
**Решение.** Claude подбирает и связывает, но не пишет теорию. Как показывать фрагмент, определяет
лицензия источника (таблица в `BRIEF.md` §3.1). Проверку выполняет код при публикации курса.

## ADR-011. Роли и вход: пользователь / админ, сессии на сервере — `принято` (владелец, 2026-10-30)
**Контекст.** Генерация контента должна быть отделена от обучения. Сгенерированное не должно попадать к
ученику без проверки человеком.
**Варианты входа.** Сессия в httpOnly-cookie + таблица сессий в Postgres · JWT в localStorage · внешний
провайдер (Keycloak, Auth0).
**Решение.** Две роли (`user`, `admin`). Сессии на сервере в httpOnly-cookie, пароли — Argon2. Проверка
прав — зависимостью FastAPI на каждом маршруте Мастерской. У контента есть статус
(`draft → checks_passed → published → archived`) и версии.
**Почему.** Для одного сервера сессия в cookie проще и безопаснее JWT: её можно отозвать, токен не
доступен JavaScript. Внешний провайдер — лишний сервис для двух учёток.
**Пересмотреть, когда** появятся несколько сервисов, которым нужно проверять вход, или вход через
внешние аккаунты.

## ADR-012. Оценка: Оценщик судит ответы вместе с кодом — `принято` (владелец, 2026-10-30)
**Решение.** Конвейер сдачи: автотесты → Ревьюер → Оценщик. Оценщик получает ответы, код, результаты
тестов и отчёт Ревьюера. Рубрика делится на «обоснование» и «реализацию», а расхождение «сказал ≠ сделал»
выделяется отдельно.
**Почему.** Ответ без кода проверяет только знание терминов. Сверка с реализацией показывает, понимает ли
ученик своё решение.

## ADR-013. Версии курса: снимок целиком в JSONB — `принято` (по умолчанию, 2026-10-31)
**Контекст.** Правка опубликованного курса не должна менять то, что уже проходят пользователи (BRIEF §5.10, п. 7).
**Варианты.**
1. *Нормализованные таблицы* `modules`, `lessons`, `blocks` с колонкой версии — версионировать каждую строку, а копирование версии = копирование дерева строк.
2. *Снимок версии* — весь курс одной JSONB-записью `course_versions.content`, схема проверяется Pydantic.
3. *Журнал изменений* (event sourcing) — история правок, версия собирается из событий.
**Решение.** Вариант 2. Черновик — отдельная строка версии; публикация переключает `courses.published_version`;
пользователь закреплён за версией в `enrollments`. Id модулей и уроков стабильны между версиями,
поэтому при переходе на новую версию пройденные уроки сохраняются.
**Почему.** Версия читается и пишется целиком, как её и редактирует админ. Старые версии неизменны без
дополнительных механизмов. Связи с библиотекой (`fragment_id`) проверяются кодом при публикации.
**Цена.** БД не следит за внешними ключами внутри JSON — это делает `publish_problems`. Отчёты «по всем
урокам» требуют обхода JSON в коде (сейчас их одна штука: где используется статья).
**Пересмотреть, когда** понадобятся запросы по урокам в SQL (статистика по урокам у многих пользователей).

## ADR-014. Сборщик: неглубокая git-копия, разбор на сервере, лицензия как проверка — `принято` (по умолчанию, 2026-10-31)
**Варианты получения.** Парсинг сайтов (HTML) · API GitHub по файлу · `git clone --depth 1 --filter=blob:none --sparse`.
**Решение.** Неглубокая разреженная копия: качаются только нужные `.md`, без истории и картинок; картинки
показываются по ссылке на тот же коммит, только если файл есть в дереве репозитория.
**Фрагмент = статья.** Поиск — полнотекстовый Postgres (`russian`), совпадение в названии весит больше.
**Безопасность.** Markdown → HTML и очистка (`nh3`, белый список тегов и схем ссылок) — на сервере при импорте;
интерфейс вставляет уже очищенный HTML. CSP разрешает картинки только с `raw.githubusercontent.com`.
**Лицензии (проверено 2026-10-31 по LICENSE.md).**
- MDN (ru): CC BY-SA 2.5 → полный текст с авторами и пометкой об изменениях.
- learn.javascript.ru: «free to read», для остального автор просит связаться; лицензия похожа на CC BY-NC
  → только оглавление и ссылка. Если автор даст согласие — поменять `license_mode` в `sources.py`.
**Контроль.** Перед импортом файл лицензии сверяется с прошлым (хэш) и с обязательной строкой; изменился —
импорт останавливается до подтверждения админом. Изменённые/пропавшие статьи помечаются «проверить»,
админ видит, в каких уроках они используются.

## ADR-015. Практические задания: версии, автопроверка, эталон не уходит ученику — `принято` (по умолчанию, 2026-10-31)
**Решение.**
- Задание хранится снимками версий, как курс (ADR-013): условие, стартовый код, эталон, проверки,
  подсказки, теория. Вид задания (веб / Python / SQL) после создания не меняется.
- Публикация только после автопроверки **именно этой редакции** (хэш спецификации): эталон проходит все
  проверки, стартовый код — хотя бы одну не проходит (иначе задание пустое).
- Эталон ученику не отправляется. Для SQL runner заранее считает ожидаемые таблицы по эталону, и в
  браузер уходят они, а не запрос.
- Код ученика автосохраняется; ученик закреплён за версией задания; подсказки открываются по одной и
  записываются в попытку. Переход на новую версию сохраняет код, но снимает «решено» — проверки могли
  поменяться.
- В уроке курса появился второй тип блока — `practice`; публикация курса требует, чтобы задание было
  опубликовано.

## ADR-016. Тесты: банк вопросов, подбор без повторов, снимки вопросов — `принято` (по умолчанию, 2026-10-31)
**Подбор (BRIEF §5.2).** По каждому вопросу темы известно, когда пользователь видел его последний раз и
верно ли ответил. Сначала берутся невиданные — равномерно по подтемам, с чередованием сложности; если их
меньше, чем вопросов в тесте, добираются виденные: сначала с ошибкой, потом самые давние. «Повторить
ошибки» собирает тест из ошибок последней попытки. Проверено тестом: две попытки подряд на банке из 50 —
ни одного повтора.
**Снимок вопроса в попытке.** Попытка хранит вопрос целиком (текст, перемешанные варианты, ответ,
объяснение, источник). Правка или архивация вопроса не меняет уже пройденные тесты. Вопрос, который
встречался в попытках, не удаляется, а уходит в архив.
**Ответ — только после завершения.** Правильность считается на сервере при каждом ответе, но в браузер
уходит только после «Завершить тест». Прерванный тест продолжается с того же места; неотвеченные при
завершении — ошибки.
**Источник обязателен.** Опубликовать вопрос без статьи из библиотеки нельзя (проверка в схеме).
Формулировки вопросов и объяснения пишет автор банка (это проверка знаний, а не теория), а теория —
по ссылке на источник. При загрузке банка `seed-quizzes` вопрос без найденного источника остаётся черновиком.
**Дубли.** Похожие формулировки в теме (Жаккар по словам ≥ 0.6) — предупреждение с возможностью
сохранить всё равно.
**Пересмотреть, когда** понадобится интервальное повторение или вопросы с открытым ответом
(тогда их оценивает Оценщик, этап 6).


## ADR-017. Генерация и наставник: шаги в очереди, черновик по урокам, ответ потоком через базу — `принято` (по умолчанию, 2026-10-31)
**Генерация (BRIEF §5.10).** Заявка → план → черновик → автопроверки → проверка → публикация. План и
черновик — задачи очереди `agent` (ADR-004); статус и «что агент делает сейчас» («читает index.html»)
пишутся в заявку, экран обновляется опросом раз в 2 секунды. Claude отвечает строго по JSON-схеме
(`output_format` Agent SDK), ответ проверяется pydantic-схемами платформы: неверный вопрос или задание не
теряются молча, а попадают в заметки урока.
**Черновик — по одному уроку за обращение.** Прогресс виден по шагам; упавший урок не теряет готовые, повтор
пропускает их. «Переделать урок» меняет только его блоки и удаляет его старые черновики, кроме того, что
уже видели пользователи.
**Создаётся обычный контент.** Курс, задания и вопросы — те же черновики, что и при ручном создании (ADR-013,
015, 016): их правят в тех же редакторах, и для них работают те же проверки публикации. Задания проходят
автопроверку runner; если она не прошла, Claude получает отчёт и один раз исправляет задание, дальше
решает админ. Ревьюер эталонов — этап 5 (шаг показан как «пропущен»).
**Публикация — всё или ничего.** «Опубликовать всё» сначала собирает все проблемы (задания, вопросы без
источника, курс) и публикует, только если их нет: пользователь не увидит половину курса.
**Права агента.** Встроенные инструменты — только Read и Glob в папке проекта (хук PreToolUse запрещает
выход за папку и файлы-секреты); Bash, Write, Edit и веб не даны. Теория — только через инструменты
библиотеки (`library_search`, `library_fragment`), id статей проверяются кодом.
**Наставник (BRIEF §5.7).** Вопрос → очередь `chat` (свой поток в agent-worker, чтобы не ждать генерацию) →
воркер дописывает ответ в базу кусками → API отдаёт их браузеру по SSE. Токен Claude нужен только
воркеру, поток переживает переподключение (текст в базе). Контекст собирается на сервере: урок и его
статьи или условие задания, код из редактора и результаты последней проверки; эталон наставник не видит.
Подсказки по нарастающей; каждая отмечается в работе над заданием и в следующей попытке (`mentor_hints`).
Просьбу «сделай курс» наставник переадресует кнопке «Предложить тему» — заявка уходит админу.
**Лимит подписки.** Генерация курса из 4 уроков упёрлась в 5-часовой лимит на втором уроке: ошибка
показывается человеческими словами со временем сброса, «Продолжить черновик» продолжает с упавшего урока.
**Приёмка (2026-10-31).** Курс по `fisht-trails` (4 урока, 4 веб-задания — все прошли автопроверку с первого
раза, 20 вопросов, 12 статей) был не виден пользователю до «Опубликовать всё» и появился сразу после.
**Пересмотреть, когда** пользователей станет много: опрос базы для SSE заменить на LISTEN/NOTIFY, а
очередь `chat` — на несколько воркеров.

## ADR-018. Граф проекта вместо чтения файлов; токены — только по запросу — `принято` (владелец, 2026-10-31)
**Проблема.** Наставник разбирался в проекте, читая файлы подряд: на fisht-trails это ~120 КБ своего кода
(~35 тыс. токенов) на каждый план и урок.
**Решение.** Анализатор `projectmap/graph.py` строит граф без модели: файлы, связи (HTML → CSS/JS, импорты
JS и Python), каркас страниц, заголовки, id и классы, CSS (раскладка, @media, переменные), функции, классы
с полями, константы, что ищет JS на странице, перекрёстные связи (битые якоря, стили без разметки и
наоборот). Библиотеки и секреты не разбираются. Карта fisht-trails — ~5 КБ вместо ~120 КБ.
Агенту граф приходит трижды: карта — прямо в задании плана; оглавления файлов урока — в задании урока;
инструменты `project_map` / `project_file` и скилл `razvilka:project-graph` (плагин в `agent/plugin`) — для
остального. Read остаётся только за точными строками; Glob убран; чтение vendor и `*.min.*` запрещено хуком.
Тот же анализатор — скилл `project-graph` для Claude Code в `ProjectsWithClaude/.claude/skills`.
**Почему не tree-sitter (ADR-008).** Для HTML/CSS/JS/Python хватает стандартной библиотеки (`ast`,
`html.parser`, регулярные выражения): ноль зависимостей, тот же файл работает как скрипт скилла.
tree-sitter понадобится на этапе 8 для вызовов функций и других языков.
**Токены в простое — ноль.** Claude вызывается только в двух местах: шаг генерации и ответ в чате; CLI
запускается на одно обращение и завершается. Статус, история чата, открытие панели, песочница, тесты,
автопроверки runner — без Claude. В CLI выключены телеметрия, автообновление и прочий служебный трафик,
в чате пустой список скиллов (их описания не уходят в каждый запрос). Расход каждого обращения — в
метрике `razvilka_agent_tokens_total` (панель Grafana) и в шагах генерации («токенов: … тыс.»).
**Проверка.** Живой вопрос по fisht-trails: агент открыл граф и оглавление `js/main.js`, ни одного файла
целиком, ~12 тыс. токенов на входе (из них 6,6 тыс. — кэш) и 0,5 тыс. на выходе.

## ADR-019. Ревьюер: чистый лист без инструментов, вердикт считает код — `принято` (по умолчанию, 2026-10-31)
**Независимость технически (BRIEF §5.9).** Каждое ревью — отдельный вызов Claude без истории. На входе
только условие, код с номерами строк и включённые правила. Инструментов нет совсем (ни файлов, ни
библиотеки, ни сети): код приходит в задании, поэтому Ревьюеру нечего читать сверх него. Эталон,
подсказки, имя ученика и переписка с наставником в задание не попадают — это проверено тестом.
**Ответ проверяет код.** Модель отвечает по JSON-схеме; платформа отбрасывает замечания с несуществующим
правилом или файлом, сбрасывает неверный номер строки, а вердикт (`changes_requested`, если есть blocker или
major) считает сама. Отброшенные замечания хранятся и считаются в отчёте.
**Правила — данные с версиями.** Первая версия разбирается из `REVIEWER.md`; админ правит, включает и
выключает правила в Мастерской → Оценивание, каждое сохранение — новая версия; отчёт помнит свою.
**Где работает.** «Ревью кода» в песочнице (ученик, по кнопке — токены только по запросу); ревью эталона —
автопроверка перед публикацией задания (в генерации запускается само после runner; вручную — кнопкой в
редакторе задания). Ревью привязано к хэшу спецификации: изменили эталон — нужно новое ревью. Замечания
можно принять с пояснением — оно видно в отчёте. Без Claude задание не опубликовать: шлюз честный.
**Очередь.** Свой поток `review` в agent-worker: ревью не ждёт генерацию курса и чат.
**Экспорт.** Тот же системный текст и правила — агент Claude Code `.claude/agents/reviewer.md`
(`app.cli export-reviewer` или кнопка в Мастерской).
**Приёмка (2026-10-31).** Живое ревью стартового кода задания: 4 blocker TASK-01 с точными строками и 2 minor
WEB-02 (контраст), ~8 тыс. токенов. Агент в Claude Code на `app.py` с инъекцией нашёл SEC-02, SEC-03, SEC-01
и вернул строгий JSON.

## ADR-020. Сдачи и Оценщик: конвейер по очередям, «сказал ≠ сделал» проверяет код — `принято` (по умолчанию, 2026-10-31)
**Практикум** — условие, развилки (вопрос, контекст, скрытый до оценки ответ эталона), автотесты (Python —
функции `test_*` против модулей сдачи, веб — `test(...)` на 375/768/1280 плюс базовые проверки страницы),
эталонные проекты и порог зачёта. Сдача — zip (до 20 МБ) или папка из ProjectsWithClaude; берётся только
текст, node_modules/сборки/бинарное/секреты отбрасываются с предупреждением; библиотеки (vendor, *.min.*)
идут в автотесты, но не в оценку. Файлы сдачи — в JSONB: проверка воспроизводима и не нужен общий том.
**Конвейер** (BRIEF §5.11): автотесты в runner (без сети, с лимитами) → Ревьюер (новый вид ревью `project`)
→ Оценщик; оба последних — в потоке `review` agent-worker, каждый отдельной чистой сессией без инструментов.
**Оценщик** получает ответы в формате ADR, «что сделал», код с номерами строк, результаты тестов, отчёт
Ревьюера, рубрику, эталоны и выборы прошлых сдач этого практикума (общая картина); ответ эталона по развилке
ему не подсказывается. Он ставит баллы 0–5 по рубрике и находит «сказал ≠ сделал».
**Код не доверяет модели.** Расхождение засчитывается, только если файл и строка есть в сдаче, а цитата
действительно из слов ученика (ответы или «что сделал»); остальное отбрасывается и считается в отчёте.
Итог = среднее блоков «обоснование» и «реализация» − штраф (по умолчанию 0,75) за каждое из первых двух
подтверждённых расхождений; зачёт — итог ≥ порога, тесты пройдены и нет расхождений.
**Рубрика** версиями, как правила Ревьюера (Мастерская → Оценивание); сдача помнит свою версию.
**Журнал «Развилки»** — решения из последних оценённых сдач с расхождениями и ответом эталона; выгрузка в
формате `DECISIONS.md`.
**Приёмка (2026-10-31).** Сдача журнала походов: в ADR «PostgreSQL с миграциями Alembic», в коде sqlite3 →
расхождения `storage.py:3` (`import sqlite3`) и `storage.py:12` (`CREATE TABLE IF NOT EXISTS` при каждом
подключении), автотесты 3/3, у Ревьюера три major. По итогам приёмки штраф ограничен двумя расхождениями
(дальше R5 и R7 уже стоят на нуле) и цитаты проверяются ещё и по «что сделал».

## ADR-021. Тренажёр архитектуры: задания в коде, материалы закреплены на коммите, схемы строит код — `принято` (по умолчанию, 2026-11-01)
**Материалы — настоящие файлы открытых проектов** (BRIEF §5.4): compose и манифест Kubernetes, дерево
репозитория, models.py/crud.py, email_server.py — из fastapi/full-stack-fastapi-template (MIT),
GoogleCloudPlatform/microservices-demo и microservices-demo (Apache-2.0), плюс compose самой Развилки.
Каждый файл закреплён на коммите (ссылка «оригинал на коммите»), лицензионные заголовки сохранены, текст не меняется.
**10 заданий по нарастающей:** 5 «выбрать» → 3 «собрать схему» → 2 «своими словами»; оба уровня — верхний
(тип архитектуры, смежные сервисы, как сервисы находят друг друга, поток данных) и нижний (наследование,
подмена реализации, граф вызовов, слои).
**Авто-диаграммы без Claude:** compose — depends_on/links/упоминания хостов в env и command; Kubernetes —
адреса сервисов в env и LoadBalancer; Python — наследование, поля-ссылки на классы модуля, граф вызовов.
Генератор показывает только объявленное — поэтому в Sock Shop он видит две связи из пятнадцати, а в Развилке
стрелки воркеров ведут к api (depends_on), хотя данные они берут из Postgres; оба факта — часть урока.
Тест сверяет ключ задания про crud.py с тем, что генератор находит в коде: ответ не выдуман.
**Проверка:** выбор и схему — код (схема: верная стрелка 1, перепутанное направление ½, лишняя −½, от числа
ожидаемых). «Своими словами» — Claude в чистой сессии без инструментов по ключевым пунктам; пункт засчитан,
только если приведённая цитата действительно есть в ответе; балл считает код.
**Засчитывается первый ответ** (правка владельца, 2026-11-01): после него открыт разбор с правильным ответом,
поэтому повтор ничего не проверяет. В «выборе» повтор закрыт; в схеме и «своими словами» можно тренироваться,
но такие попытки помечены и на балл не влияют. Если оценка «своими словами» не удалась (Claude недоступен),
попытка не сгорает. В материалах своего проекта убраны комментарии, которые называли ответ (чужие файлы — как
есть, по лицензии); под файлом это указано.
**Почему задания в коде, а не в базе.** Материал и ключ ответа — одно целое и меняются вместе с проверкой
согласованности в тестах; попытки хранятся в базе. Генерация заданий тренажёра в Мастерской — следующий шаг.
**Приёмка (2026-11-01).** 10 заданий на четырёх реальных проектах; в браузере собрана схема Sock Shop (верные,
перепутанная и лишняя стрелки размечены, балл 1,0 = (3 + ½ − ½) / 15 × 5); живое «своими словами» по
models.py/crud.py — 4 пункта из 6 с цитатами, пропущенные (verify_password, DUMMY_HASH) названы точно.

## ADR-022. Путь «напиши заново сам»: этап = практикум, эталон = проект автора, рабочая папка на диске — `принято` (по умолчанию, 2026-11-01)
**Устройство (BRIEF §5.5).** Путь строит админ в Мастерской → Генерация (вид «путь»). План — 3–6 этапов от пустой
папки до готового проекта, у каждого цель, файлы, статьи библиотеки и 1–2 развилки; плюс роли частей проекта.
Черновик — по этапу за обращение: условие, развилки с ответом автора (со ссылками на файлы) и автотесты.
Этап хранится как практикум этапа 6 (`assignments.path_id`, номер, цель, файлы) — сдаётся тем же конвейером
автотесты → Ревьюер → Оценщик, а ответ автора открывается после оценки.
**Автопроверка этапа без Claude:** тесты обязаны проходить на оригинальном проекте (он и есть эталон) и падать на
пустой папке; оригинал едет в runner вместе с задачей — у runner нет доступа к папкам владельца. Не прошло —
Claude один раз чинит тесты по отчёту. Ревьюер эталона не нужен: эталон — код автора как есть.
**Рабочая папка** — `razvilka/workspace/<логин>/<путь>/` (том `./workspace:/workspace` у api): ученик пишет в
своём редакторе, оригинал не копируется. Этапы открываются по порядку: следующий — когда засчитан предыдущий
(проверка на сервере). Карта оригинала — граф без Claude и роли частей от Claude; код автора ученику не показываем.
**Превью рабочей папки** — `/api/preview/<подписанный токен>/…`: HMAC-ссылка на 4 часа и заголовок
`Content-Security-Policy: sandbox allow-scripts`, плюс `sandbox` у iframe — код ученика выполняется в изолированном
источнике и не может прочитать cookie или вызвать API платформы (проверено в Chromium: `SecurityError`).
**Приёмка (2026-11-01).** Путь по fisht-trails: 4 этапа, у каждого две развилки; автопроверки 4/4 (на оригинале
11/11/12/17 тестов проходят, на пустой папке — нет); опубликован одной кнопкой, до публикации ученик его не видел.
Этап 1 сдан из рабочей папки: автотесты 11/11, у Ревьюера major WEB-02 (контраст ссылок 2,7:1), Оценщик — 3,0,
без расхождений → засчитан, открылся этап 2; после оценки показан ответ автора (Bootstrap 5.3.3 локально).

## ADR-023. Пауза генерации: флаг в заявке, точки остановки и прерывание вызова Claude — `принято` (2026-11-01)

**Контекст.** Длинный черновик курса может упереться в 5-часовой лимит подписки посреди урока. Админ хочет остановиться сам, пока лимит не кончился, и продолжить после сброса.

**Решение.** У заявки поле `pause` (`after` | `now`) и статус `paused`. Конвейер проверяет флаг между уроками, перед автопроверками и перед каждым ревью эталона. `now` прерывает и сам вызов Claude: `run_structured(should_stop=…)` проверяет флаг на каждом сообщении агента и закрывает поток `query()`, процесс CLI завершается. Недописанный урок отбрасывается, готовые уже в базе; «Продолжить» ставит ту же задачу, готовые уроки и уже проверенные эталоны пропускаются.

**Цена.** «Остановить сейчас» теряет токены, уже потраченные на прерванный урок. Пауза срабатывает на границе хода агента, а не посреди генерации ответа.
